# Deep-Research Review: sisu v2.2 — Enforcement-Semantics Verification & Comparative Tool Survey

*All findings current as of August 21, 2026, and date-stamped to their primary sources.*

## TL;DR
- The spec's core security thesis holds and is VERIFIED against primary docs: local git hooks are advisory (defeatable by `git push --no-verify`, `git -c core.hooksPath=/dev/null push`, or editing the tracked hook), real enforcement lives server-side in GitHub org rulesets, and commit-status spoofing is real unless a required check is bound to a specific GitHub App.
- Two spec claims are STALE and must change: org-level "require workflows to pass before merging" is no longer Enterprise-only (org rulesets — including required workflows — reached GitHub Team plans on **June 16, 2025**), and "Workflow execution protections" entered **public preview** (GitHub Changelog, June 18, 2026) at repo/org/enterprise scope with actor rules, event rules, and evaluate mode.
- sisu's central novelty claim — actor-relative enforcement honesty (reporting which guardrails are real walls and against which actor) — is **confirmed genuinely novel**; no surveyed tool (Scorecard, Legitify, Allstar, Minder, zizmor, Betterer) reports guardrails relative to a threat actor, though sisu should mine their probe/rule inventories.

## Details — Part 1

### Claim 1 — Local git hooks are advisory
**Status: VERIFIED.** The official git-scm `githooks` documentation confirms hooks live in `$GIT_DIR/hooks` but "that can be changed via the core.hooksPath configuration variable." Because a command-line `-c core.hooksPath=/dev/null` overrides repository config for a single invocation, and `git push --no-verify` skips the pre-push hook, a repo-managed hook cannot enforce policy against a motivated local actor; a tracked hook can also simply be edited. `core.hooksPath` was added in Git 2.9.0 (June 2016); no recent git version has changed the fundamental precedence — command-line `-c` outranks local (`.git/config`) > global (`~/.gitconfig`) > system (`/etc/gitconfig`). Pro Git's guidance that policy enforcement belongs server-side is accurately represented.
**Implication:** No change needed. sisu is correct to classify hooks as advisory/"speed-bump" against the repo owner, real only against an honest agent.

### Claim 2 — Repo-level rulesets bypassable by repo admins
**Status: VERIFIED.** Per GitHub Docs ("Available rules for rulesets"): "People with admin access to a repository, or a custom role with the 'edit repository rules' permission, can create, edit, and delete rulesets for a repository." Repo admins can also add bypass actors including the "repository administrator" role. So a repo-level ruleset is honestly `bypassable-by: repo-admin`.

### Claim 3 — Org-level rulesets
**Status: VERIFIED (with a plan-availability date).** Organization rulesets can only be tightened, never weakened, by repo admins — GitHub aggregates rules most-restrictively; when multiple rulesets target the same branch the union of rules applies and the most restrictive wins. Org rulesets became available to GitHub Team plans per the **GitHub Changelog, June 16, 2025** ("Organization rulesets now available for GitHub Team plans"): "GitHub Team plans can now configure and enforce organization-level rulesets! Previously, this powerful governance capability was limited to Enterprise plans... Enforce requirements such as requiring pull requests, requiring GitHub Actions workflows, and more organization-wide." Ensure the spec's Team-plan claim is dated to this changelog.

### Claim 4 — Org "require workflows to pass before merging"
**Status: STALE / OUTDATED in the spec.** Historically this GA'd for GitHub Enterprise Cloud only, but the same June 16, 2025 changelog explicitly lists "requiring GitHub Actions workflows" among the org-level rule capabilities newly available to Team plans. Current docs list "require workflows to pass before merging" as configurable at organization or enterprise level (not repository-level rulesets), supporting the `pull_request`, `pull_request_target`, and `merge_group` events. Note a documented gotcha: any event filters (branches, paths, types) are ignored — the workflow is always triggered by the default activity types.
**Implication:** Drop "Enterprise-only"; state that org-level required-workflows is available to Team plans as of June 2025, at org/enterprise scope only.

### Claim 5 — Workflow execution protections + 2026 roadmap
**Status: UPDATE — now in public preview.** Per the **GitHub Changelog, June 18, 2026** ("Control who and what triggers GitHub Actions workflows"): "Workflow execution protections are now in public preview for GitHub Enterprise, organizations, and repositories... built on the GitHub rulesets framework." They provide **actor rules** (individual users, repo roles Read/Maintain/Admin, GitHub Apps, Copilot, Dependabot) and **event rules** (push, pull_request, pull_request_target, workflow_dispatch), scope via repository custom properties, and support **evaluate mode** (would-be blocks surface in policy insights). GitHub's "What's coming to our GitHub Actions 2026 security roadmap" blog frames these plus additional forthcoming rules; the ecosystem separately tracks workflow lockfiles / transitive-dependency pinning, immutable actions, and SHA-pinning enforcement.
**Implication:** Update the spec from "unknown/not available" to "public preview (June 2026), repo+org+enterprise, actor+event rules, evaluate mode."

### Claim 6 — Ruleset enforcement status semantics
**Status: VERIFIED.** Rulesets have three enforcement statuses: **Active**, **Evaluate** (rules run but are not enforced; would-be blocks appear in Rule Insights / the rule-suites REST API), and **Disabled** (both Evaluate mode and the rule-insights dashboard are documented as public preview). Bypass actors can be roles, teams, GitHub Apps, and deploy keys; anyone on the bypass list makes the rule non-binding for them — the key honesty point. The REST rulesets API exposes `enforcement` (active/evaluate/disabled), `bypass_actors` (with `actor_id`, `actor_type`, `bypass_mode`), `source`/`source_type` (Repository/Organization), and `conditions` for probing. Evaluate mode availability follows ruleset plan availability (public repos on Free; Pro/Team/Enterprise Cloud for private).

### Claim 7 — Commit-status spoofing & app binding
**Status: VERIFIED.** Per GitHub Docs ("Status checks"): "Anyone with write permissions to a repository can set the state for any status check in the repository." A **job** that is skipped reports "Success" and satisfies a required check. Required status checks can be bound to a specific GitHub App per the **GitHub Changelog, Dec 1, 2021**: "You can now control which GitHub App a required status check is provided by. If status is then provided by a different app or by a user via a commit status, merging will be prevented." The app must be installed with `statuses:write`, must have recently submitted a status, and the check must be associated with a pre-existing required status check; newly added required checks default to the app that most recently reported. If a check and a commit status share the same name and that name is required, both must pass. Critical distinction: GitHub Actions produces **checks** (only creatable by GitHub Apps via the Checks API — "Write permission for the REST API to interact with checks is only available to GitHub Apps"), whereas the Statuses API creates **commit statuses** (any write-permission actor). The REST API exposes `required_status_checks` with `app_id`/`integration_id` in both the branch-protection and rulesets APIs, enabling sisu to probe check-to-app binding.

### Claim 8 — CODEOWNERS
**Status: VERIFIED.** CODEOWNERS is read from the **base branch** of the PR; valid locations are `.github/`, repo root, or `docs/`; last-matching pattern wins; the file must be **under 3 MB** ("A CODEOWNERS file over this limit will not be loaded, which means... the appropriate code owners will not be requested to review changes"); any line with invalid syntax is silently skipped ("If any line in your CODEOWNERS file contains invalid syntax, the file will not be detected and will not be used"); an owner without write access, or a non-visible team, is silently ignored; and `!` negation is unsupported (treated as invalid). "Require review from Code Owners" must be separately enabled in branch protection or a ruleset. The net effect: an invalid entry or oversized file **silently disables** owner-review enforcement for affected paths while the branch/ruleset rule still shows as configured.
**Implication:** sisu's `doctor` should probe: CODEOWNERS presence, size < 3 MB, syntax validity, that the CODEOWNERS file itself is owned (`/.github/CODEOWNERS @owner`), and that the code-owner-review rule is enabled — because all of these fail silently.

### Claim 9 — Required-check skip semantics
**Status: VERIFIED.** Per GitHub Docs and community discussion #54877: a workflow skipped due to **path filtering, branch filtering, or a commit message** leaves associated checks in **"Pending"** and blocks merge ("A pull request that requires those checks to be successful will be blocked from merging"); a **job** skipped via a job-level `if:` conditional reports **"Success"** and satisfies a required check. Successful check statuses are **success, skipped, and neutral**. GitHub explicitly warns: "You should not use path or branch filtering to skip workflow runs if the workflow is required to pass before merging." For merge queues, workflows must add the `merge_group` trigger or the required check never reports and the merge fails. The `always()` aggregator pattern and `re-actors/alls-green` / `dorny/paths-filter` / `poseidon/wait-for-status-checks` deciders are the standard workarounds; the key gotcha is that an aggregator job depending on skipped jobs is itself "skipped" (which auto-merge treats as success) unless it explicitly inspects results.
**Implication:** sisu's emitted verdict/aggregator job must use an explicit alls-green result check, not rely on "job skip = success."

### Claim 10 — Actions supply-chain hardening
**Status: VERIFIED.** Pinning to a full-length commit SHA is documented as "currently the only way to use an action as an immutable release." **Immutable releases reached GA per the GitHub Changelog, Oct 28, 2025** ("Immutable releases are now generally available": "Once you publish a release as immutable, its assets can't be added, modified, or deleted"); **immutable actions** are a separate roadmap item (#1103) still rolling out. A GitHub Actions policy (Changelog, Aug 15, 2025) now supports blocking actions and requiring full-SHA pinning. The **Dec 8, 2025** change (announced Nov 7, 2025) makes `pull_request_target` **always source its workflow file and checkout ref from the default branch** — "GITHUB_REF for pull_request_target will resolve to the default branch, and GITHUB_SHA will point to the latest commit on that branch" — closing the "zombie workflows" vulnerability class (Sonar reported 188 such vulns). `pull_request_target` and `workflow_run` remain the primary untrusted-checkout risks. `GITHUB_TOKEN` should be least-privilege (`permissions: {}` at workflow level, minimal per-job grants); `${{ }}` interpolation of untrusted input remains the top script/expression-injection vector.

### Claim 11 — Codex AGENTS.md discovery
**Status: VERIFIED; one spec correction.** Per official OpenAI Codex docs (developers.openai.com/codex/guides/agents-md): Codex walks root-down, concatenates files joined by blank lines (closer-to-CWD files take precedence on conflict), **skips empty files**, and "stops adding files once the combined size reaches the limit defined by project_doc_max_bytes (32 KiB by default)." This is a **combined, whole-chain cap**, not per-file, confirmed in the Codex source (`pub(crate) const PROJECT_DOC_MAX_BYTES: usize = 32 * 1024; // 32 KiB`, with "Larger files are silently truncated to this size"). The default has **not** changed to 64 KiB — `65536` appears in third-party guides only as a user-raised example. `project_doc_fallback_filenames` are consulted only when AGENTS.md is absent at a level; `AGENTS.override.md` **replaces** (not extends) AGENTS.md at its level; `CODEX_HOME` relocates the `~/.codex` home. The AGENTS.md standard was donated to the Linux Foundation's Agentic AI Foundation (Dec 2025).
**Implication:** Keep sisu's cap documentation at 32 KiB combined with silent truncation; do not assume 64 KiB.

### Claim 11b — AGENTS.md per-tool auto-load status
**Status: VERIFIED (observed vs advisory calibration).**
- **Native auto-load (observed)**: OpenAI Codex CLI, GitHub Copilot (coding agent + VS Code), Cursor, Google Jules, Sourcegraph Amp, Windsurf/Devin, Zed, Factory, opencode, Cline.
- **Requires config (advisory)**: Gemini CLI — default is `GEMINI.md`; AGENTS.md loads only if added to `context.fileName` in settings.json (issue google-gemini/gemini-cli#28227 open, filed July 1, 2026).
- **No auto-discovery**: Aider — needs explicit `--read` or a `read:` entry in `.aider.conf.yml`.
- **Claude Code**: does not natively load AGENTS.md at runtime; the standard workaround is `@AGENTS.md` import from CLAUDE.md (support requests, e.g., issue 50778, open as of Aug 2026).
**Implication:** sisu's per-tool "automatic-load status" table should mark Codex/Copilot/Cursor/Amp/Zed/etc. as *observed-native*, Gemini CLI and Aider as *advisory/needs-config*, and Claude Code as *needs-import-shim*.

### Claim 12 — Claude Code as emit target
**Status: VERIFIED with nuances (official docs + targeted research).**
- **Hooks**: `.claude/settings.json` supports PreToolUse/PostToolUse (plus Stop, SessionEnd, UserPromptSubmit, etc.). Exit code 2 = blocking error (PreToolUse blocks the tool call; PostToolUse surfaces stderr to Claude even though the tool already ran). JSON stdout supports `hookSpecificOutput.permissionDecision` = allow/deny/ask, plus universal `continue`/`decision`/`reason`. Exit 2 blocks even when JSON says "allow."
- **Hook timeout — 60s default is now STALE.** As of **v2.1.3** the default is **600 seconds (10 min)** for command/http/mcp_tool hooks; prompt hooks 30s; agent hooks 60s; UserPromptSubmit 30s. **v2.1.208** changed a UserPromptSubmit callback timeout from "ends the turn with an execution error" to "blocks the prompt + continues"; **v2.1.210** (July 14, 2026) fixed hook timeouts being misreported to the model as user rejections (which had stalled unattended sessions).
- **Subagents**: `.claude/agents/*.md` (project) or `~/.claude/agents/*.md` (user) use YAML frontmatter — `name`, `description`, `tools` (comma-separated allowlist; inherits all if omitted), `disallowedTools`, `model` (sonnet/opus/haiku/inherit), `permissionMode`, `maxTurns`, `skills`, `mcpServers`. On name collision the most-specific/closest wins.
- **Settings precedence** (highest→lowest, per official settings docs): **Managed settings** (`managed-settings.json`; macOS `/Library/Application Support/ClaudeCode/`, Linux/WSL `/etc/claude-code/`, Windows `C:\ProgramData\ClaudeCode\`) → **command-line args** → `.claude/settings.local.json` (project-local) → `.claude/settings.json` (shared project) → `~/.claude/settings.json` (user). Same-named list keys (e.g., `permissions.allow`) **merge**, not override. Env vars are not a precedence level.
- **Schema validation**: An official published JSON schema exists for **settings.json** (`https://json.schemastore.org/claude-code-settings.json`, now linked from the settings docs, "gives you autocomplete and inline validation... The schema can lag behind the newest CLI releases") and for plugin/marketplace manifests (SchemaStore). No official JSON schema exists for **subagent frontmatter** or **SKILL.md** — community-only (e.g., hesreallyhim/claude-code-json-schema, explicitly unaffiliated) — **UNVERIFIABLE**.
- **Hermetic self-verification**: `CLAUDE_CONFIG_DIR` is officially documented ("To keep the home-directory files somewhere else, set `CLAUDE_CONFIG_DIR`; Claude Code then stores your settings, session history, and plugins there instead") and confirmed active (referenced in v2.1.208 release notes). It enables an isolated user-config cold-load, but project-local `.claude/settings.local.json` is still written into the workspace (GitHub #3833), so isolation is partial and Anthropic does not document a formal "hermetic self-verification" flow — treat as **PARTIALLY VERIFIABLE**.
- **Release cadence**: Claude Code ships very frequently (multiple 2.1.x patch releases through mid-2026), which validates sisu's per-target "contract version" pinning.

## Details — Part 2: comparative tool survey, mapping & borrow list

### A. SCM posture scanners / enforcers
- **OpenSSF Scorecard (v5.5.0, Apr 23, 2026)** — architecture: read-only probe/scorer. Assesses projects against **18 security checks** spanning three themes (holistic security practices, source-code risk, build-process risk). Directly relevant checks: **Branch-Protection, Token-Permissions, Pinned-Dependencies, Dangerous-Workflow**. v5 introduced **Structured Results / probes**: checks broken into individual heuristics runnable via `--probes name1,name2 --format probe`, each in an experimental/stable/deprecated lifecycle state. *Overlap with sisu*: this is the closest architectural analog to sisu's `doctor --remote` probes. **Borrow**: the granular, individually addressable, stable-versioned probe model; mine the Dangerous-Workflow and Token-Permissions heuristics. *Caveat*: peer-reviewed research found no clean correlation between high scores and fewer vulnerabilities — it's a hygiene signal, gameable — which reinforces sisu's honesty framing.
- **OpenSSF Allstar** — architecture: continuous **active enforcement** GitHub App. Monitors GitHub API state and either logs, files an issue, or **reverts** drifted settings. *Overlap/contrast*: the polar opposite of sisu's never-mutate-remote stance. Its distinctive value is catching stealthy temporary weakening of branch protection ("Allstar will detect and respond to a policy violation if someone temporarily disables branch protections in order to commit"). **Borrow**: the detect-drift-then-alert half only; sisu correctly declines the mutation half.
- **Legitify (Legit Labs)** — architecture: read-only scanner, OPA-policy-based, across five namespaces — **organization, actions, member, repository, runner_group** — with text/JSON/SARIF output. Requires a **classic PAT** with scopes `admin:org, read:enterprise, admin:org_hook, read:org, repo, read:repo_hook` (fine-grained PATs unsupported because they lack GraphQL). **Borrow**: the namespace taxonomy and specific policy names (`requires_status_checks`, `no_conversation_resolution`, "Code Review By At Least Two Reviewers Is Not Enforced," "Two-Factor Authentication Is Not Enforced," "Stale Admin Found," "GitHub Actions Runs Are Not Limited To Verified Actions") as a probe checklist — and its honest "skipped due to insufficient permissions" reporting, which mirrors sisu's actor-relative honesty.
- **Chain-bench / Minder (Stacklok, OpenSSF sandbox)** — Minder is policy-as-code enforcement across repos (branch protection, secret scanning + push protection, Dependabot/CodeQL enablement) with alert-or-auto-remediate and Sigstore/attestation verification. **Borrow**: the reusable profile format and the enable-secret-scanning/push-protection checklist.
- **GitHub security configurations / rulesets insights** — native probe surface via the rule-suites REST API; sisu's `doctor --remote` should read it directly.

### B. Workflow static analyzers
- **zizmor** — broad Actions auditor. Rule inventory to mine as an attack-shape catalog: `unpinned-uses`, `template-injection`, dangerous-trigger detection, `artipacked` (persisted checkout credentials), `impostor-commit`, `typosquat-uses`, `known-vulnerable-actions`, `dependabot-cooldown`, plus `github-env` injection and excessive-permissions checks. Personas: regular/pedantic/auditor; severity/confidence thresholds; SARIF/GHAS integration; some audits are online (need a token). **Borrow**: the rule inventory and the persona/threshold model for tunable strictness.
- **actionlint** — lint-heavy with shellcheck integration; deterministic, fast, good as a blocking PR gate. **poutine** — supply-chain-focused with wide coverage. **StepSecurity Harden-Runner / Secure Repo** — runtime egress control + config generation. **sethvargo/ratchet** and **pinact** — SHA-pinning tooling. **Dependabot/Renovate** — SHA-pinning support with cooldowns (Renovate `minimumReleaseAge`). **Borrow**: pin-checking logic and the "gate only *new* alerts" (Goodhart-aware) baseline pattern.

### C. Quality-ratchet prior art
- **Betterer** — snapshot ratchet (a results file; the build fails if the metric regresses).
- **ESLint bulk suppressions** — native since **v9.24.0 (Apr 2025)**: `--suppress-all` / `--suppress-rule` writes `eslint-suppressions.json`; **v9.28.0** added `--pass-on-unpruned-suppressions`. It tracks per-file per-rule **counts only**, so it cannot identify *which* specific violation changed. (Note: ESLint v9.x reached end-of-life 2026-08-06.)
- **diff-cover** — coverage on changed lines. **SonarQube "clean as you code"** — new-code quality gates; `sonar.qualitygate.wait` breaks the build.
- **Measurement-identity gap (sisu's differentiator)**: none of these bind the *measurement identity* — the exact command, config, and scope that produced the number. Betterer and ESLint baselines silently drift if the command or ruleset changes; SonarQube ties gates to server config rather than a committed, reproducible invocation. **sisu's claim that a ratchet must pin the measurement identity is well-founded and unmatched.**

### D. Agent-governance & agent-memory prior art
- Prior art exists for the *pieces*: Claude Code hooks-based guardrail projects, AGENTS.md ecosystem tooling, Cursor rules (`.cursor/rules/*.mdc`), `.github/copilot-instructions.md`, and memory systems (session memory, knowledge files, MemGPT/Letta-style external/tiered memory). But **no widely-adopted tool implements a candidate→promoted knowledge lifecycle gated by verification** and recorded in a repo audit ledger; MemGPT/Letta do memory tiering without verification-gated promotion into a repo.
- **Actor-relative enforcement honesty — CONFIRMED NOVEL.** No surveyed tool (Scorecard, Legitify, Allstar, Minder, zizmor) reports guardrails *relative to which actor they actually constrain*. Scorecard/Legitify report configuration presence/absence; none articulate "this hook is a wall against the honest agent but a speed-bump against the repo admin." sisu's enforcement-model honesty — mapping each guardrail to the actor it does/doesn't stop — is a real, defensible differentiator, as is the measurement-identity-bound ratchet.

### E. Secret-scanning gates
- **gitleaks** — config/allowlist via `.gitleaks.toml`, a **soft baseline** surface: overly broad allowlists can hide live secrets, so a sisu probe should flag broad allowlist rules and stopwords.
- **GitHub push protection** — free secret scanning on public repos; **push protection for private repos requires GitHub Secret Protection / Advanced Security**. By default anyone with write access can bypass by specifying a reason; **delegated bypass** (GA per Changelog, Oct 23, 2024) routes bypass through a reviewer list. Every bypass creates a Security-tab alert, an **audit-log** event, and email to owners/security managers — a genuine audit trail. **Borrow**: probes for whether push protection is enabled, whether delegated bypass is configured, and the breadth of `.gitleaks.toml` allowlists.

## Recommendations
1. **Fix the two stale plan-availability claims first (highest priority).** (a) Org-level "require workflows to pass before merging" is **not Enterprise-only** — it is available to **Team plans since June 16, 2025**, configured only at org/enterprise scope. (b) Add **Workflow execution protections** as a new enforcement primitive: **public preview (June 18, 2026)**, repo/org/enterprise, actor + event rules, evaluate mode. Date-stamp both.
2. **Correct the Codex cap** to **32 KiB combined** (whole-chain, silent truncation) — remove any 64 KiB assumption.
3. **Update the Claude Code contract**: hook default timeout is **600s (since v2.1.3)**, not 60s; note the v2.1.208 (UserPromptSubmit callback-timeout no longer ends the turn) and v2.1.210 (timeouts no longer misreported as user rejections) changes; cite the official `claude-code-settings.json` schema; mark subagent-frontmatter and SKILL.md schemas as unofficial; document `CLAUDE_CONFIG_DIR` for cold-load **with the caveat** that project-local `settings.local.json` still writes to the workspace.
4. **Adopt the Scorecard probe architecture** for `doctor --remote`: granular, individually addressable, stable-versioned probes. Seed the catalog from Scorecard's Branch-Protection/Token-Permissions/Dangerous-Workflow/Pinned-Dependencies and Legitify's five-namespace policy names; read the rulesets and rule-suites REST APIs (`enforcement`, `bypass_actors`, `required_status_checks.app_id`) to compute actor-relative verdicts.
5. **Harden the emitted CI aggregator** with an explicit alls-green result check rather than "job-skip = success"; always add `merge_group` to required workflows; never use path/branch filtering on a required workflow.
6. **Add CODEOWNERS silent-failure probes** (size < 3 MB, syntax validity, self-ownership of the CODEOWNERS file, and code-owner-review rule enabled) — each fails silently and can hollow out a merge gate that still *looks* configured.
7. **Foreground the two confirmed differentiators** — measurement-identity-bound quality ratchets and actor-relative enforcement honesty — in the spec's positioning; both are unmatched by existing tooling.

**Thresholds that would change these recommendations:** If GitHub GAs workflow execution protections or immutable actions (watch the changelog), promote sisu's probe from "preview" to "GA" and treat SHA-pinning enforcement as first-class. If Claude Code ships native AGENTS.md loading, drop the import-shim recommendation. If a competitor ships actor-relative enforcement reporting or measurement-identity-bound ratchets, sisu's novelty claims weaken and should be re-scoped.

## Caveats
- GitHub, Claude Code, and Codex change rapidly; all findings are dated to their primary sources and current as of Aug 21, 2026. Third-party corroborations were used only where they matched primary docs.
- "Immutable actions" (distinct from immutable **releases**, which are GA as of Oct 28, 2025) were rolling out via roadmap #1103; re-verify GA status at publication.
- No official JSON schema exists for Claude Code subagent frontmatter or SKILL.md — validation is community-only (**UNVERIFIABLE**).
- The "hermetic self-verification under a clean HOME" use of `CLAUDE_CONFIG_DIR` is inferred from documented behavior, not an officially documented workflow (**PARTIALLY VERIFIABLE**); project-local settings still write into the workspace.
- Chain-bench and StepSecurity specifics were not fetched from primary docs in this pass; treat their exact check inventories as directional rather than verified.
- Scorecard's own documentation stresses its scores are opinionated hygiene signals, not security guarantees — relevant context for how sisu should present any borrowed scoring.
